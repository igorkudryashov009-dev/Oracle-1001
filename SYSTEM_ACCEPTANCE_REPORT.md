**Найдено дословно:**

| Аспект | Что сказано в доках | Число |

| Лимит MMSI на фильтр | "max 50 MMSI per WebSocket FiltersShipMMSI" | **50, точная цифра** |
| Лимит частоты подписки | "you can send a maximum of 1 subscription update a second" | **1/сек, точная цифра** |

| SLA / стабильность | Сервис в BETA, без гарантий аптайма | — |
| Пропускная способность на сокет | Рекомендуется канал, способный обработать ~300 сообщений/сек при подписке на весь мир | 300 msg/s (ориентир, не лимит) |

**Вывод:** явного числового лимита на количество одновременных WebSocket-соединений
с одним API-ключом **в документации нет**. Есть только общая формулировка про
throttling без порога. Согласно инструкции задания, это означает: **нельзя считать
55 соединений безопасными по умолчанию**.

**Митигация, внедрённая в `collector.py` (сделано, не отложено):**

1. **Staggered rollout** — каждый батч стартует со сдвигом `batch_id × 2.5 сек`
   от момента запуска скрипта (не все 55 в первую же миллисекунду). Полный
   разворот 55 батчей занимает ≈135 сек вместо мгновенного залпа.
2. **Семафор на handshake** — не более `MAX_CONCURRENT_HANDSHAKES = 20`
   соединений одновременно находятся в фазе connect+subscribe. Семафор
   освобождается сразу после успешной подписки (или явного отказа сервера),
   то есть не ограничивает количество уже стабильно открытых сокетов —
   только скорость их набора.
3. **Логирование по каждому батчу**: `logs\collector_log.txt` содержит
   `batch[N] connect attempt @ <ts>`, `batch[N] subscribed OK ...` или
   `batch[N] UNREACHABLE this session after K consecutive handshake failures`.
   Если реальный лимит существует — он проявится как серия `UNREACHABLE`
   начиная с конкретного batch_id, что будет явно видно в логе.
4. **Graceful degradation**: не подключившиеся батчи не останавливают
   остальные (каждый батч — независимая asyncio-задача со своим backoff).
   Список недостижимых MMSI сохраняется в
   `история1\collector_unreachable_mmsi.json` (генерируется только если
   такие батчи есть).
5. CLI-параметры `--stagger-seconds` и `--max-concurrent-handshakes`
   позволяют скорректировать поведение по факту, если тест на Шаге 2 покажет
   иную реальную границу.

**Ограничение этого отчёта:** поскольку live-тест не проводился (см. §0),
**реальное эмпирическое число ещё не получено** — только теоретический
аудит доки и превентивные меры. Это отдельный пункт чек-листа в §4.

## §3. Известные операционные риски и их митигация

### 3.1. 2307 IMO без MMSI — структурное ограничение источника

`targets_missing_mmsi.csv` содержит **2307** IMO из `fleet_database.csv`, для
которых MMSI не был извлечён. **Эти суда никогда не появятся в архиве через
AIS-подписку по MMSI** — AISstream фильтрует только по MMSI
(`FiltersShipMMSI`), не по IMO. Это не баг сборщика, а структурное ограничение
источника данных.

**Митигация:** явно задокументировано в README и в `targets_missing_mmsi.csv`
(отдельный файл, не молча отброшенные строки). Если для этих 2307 судов
нужна геопозиция — единственный реалистичный вариант в рамках бюджета — это
**платный провайдер с поиском по IMO** (например Datalastic, MarineTraffic
API и т.п.), что выходит за рамки объявленного бюджета **$30/мес** и требует
отдельного решения/одобрения бюджета от пользователя. Система **не пытается**
подделать или угадать позиции этих судов.

### 3.2. Суда, месяцами не появляющиеся в потоке

AISstream — это сеть **наземных (terrestrial) AIS-станций**, покрытие
типично ограничено ~200 км от берега. Судно в открытом океане/вдали от
побережья физически не видно этой сети, даже если оно исправно передаёт AIS.
Это ограничение бесплатного источника, а не ошибка сборщика.

**Митигация:** `daily_snapshot.py` помечает такие случаи как
`data_source="no_signal_24h"`, сохраняя последнюю **известную** позицию, но
явно **не экстраполируя** её как факт. Дашборд не рисует эти суда как
"двигающиеся" — они просто не получают новых точек трека.

### 3.3. Что происходит при перезагрузке ПК / отключении

В режиме `local_scheduled`:

- **Коллектор** (`collector.py`) не переживает перезагрузку/выключение ПК —
  это отдельный долгоживущий процесс, не управляемый Task Scheduler по
  умолчанию в этой конфигурации. Пока ПК выключен, **новые точки не пишутся**
  в `raw_positions.db` — это пробел в сырых данных за период простоя.
- **Ежедневный снапшот** (Task Scheduler) зарегистрирован в режиме
  "run only when user is logged on" (без сохранённого пароля администратора).
  Если ПК выключен или пользователь не залогинен в момент триггера
  (00:05 UTC) — снапшот этого дня **пропускается** целиком, дата просто
  отсутствует в `история1\daily\`.

**Как это выглядит на дашборде:** отсутствующий день — это **пропуск в
последовательности файлов `daily/YYYY-MM-DD.csv`**, а не строка с нулевыми
значениями. Баннер архива показывает реальное количество накопленных дней
(`days_accumulated = len(файлов в daily/)`), которое **не будет равно**
количеству календарных дней с даты старта, если были пропуски — это ожидаемо
и не должно трактоваться как "система сломана". Рекомендация: если нужна
устойчивость 24/7 без пробелов — переключиться на `mode: vps_always_on`
(~$5/мес, инструкция в README, укладывается в бюджет $30/мес).

Допущения (явно проговорены, а не скрыты):
- Типичная индустриальная практика для терминальных AIS-агрегаторов (не
  спутниковых) — от **40% до 75%** флота дают хотя бы 1 точку в сутки,
  в зависимости от того, сколько судов в момент замера находится в открытом
  океане vs. в прибрежных водах / портах. Точная доля станет известна только
  из живого теста.
- 1 позиционный репорт в среднем каждые ~10 сек — 1 мин для судна в зоне
  покрытия при обычном трафике AIS (Class A cargo/tanker).

| Горизонт | Ожидаемое кол-во дней в `daily/` (при условии, что ПК/задача работают без пропусков) | Ожидаемый суммарный объём `raw_positions.db` (оценка) | Ожидаемая доля судов с ≥1 точкой хотя бы раз за период |
